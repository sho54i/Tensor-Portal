The 402 Origin Story

A status code reserved in 1991, finally fulfilled 34 years later.

Foundation

When Tim Berners-Lee and the HTTP/1.0 authors designed the web, they reserved status code 402 "Payment Required" for a future where the internet could natively transact value. The technology to fulfil it — cheap finality, programmable tokens, machine-readable wallets — didn't exist. It sat unused for three and a half decades.

By 2025, three conditions converged simultaneously: stablecoins with programmable authorization (USDC on Layer-2 chains), sub-cent gas fees on networks like Base and Solana, and AI agents capable of signing transactions without human intervention. Coinbase shipped the first x402 reference implementation on May 6, 2025. The code filled in the blank that HTTP left open.

Protocol Architecture

The four-party model and one-round-trip payment handshake.

x402 extends a normal HTTP request-response cycle with a single new step: a cryptographically verifiable payment handshake that settles onchain in the background. Everything flows over standard HTTP; the blockchain runs through a Facilitator — an optional but recommended service that abstracts node interaction.

01
Client Request
Agent or app sends a standard GET/POST to a protected endpoint. No credentials attached.
HTTP REQ
02
402 Challenge
Server returns HTTP 402. Payment terms encoded in the PAYMENT-REQUIRED header (base64 JSON).
HTTP 402
03
Client Signs
Client reads the terms, generates an EIP-3009 / EIP-712 typed-data signature, attaches it as PAYMENT-SIGNATURE header, and retries.
SIGN + RETRY
04
Facilitator Verify
Server forwards payload to Facilitator's POST /verify. Facilitator confirms signature validity and settles onchain.
SETTLE
05
Resource Served
Server returns the resource with PAYMENT-RESPONSE receipt header. Entire flow: one round trip, <200ms typical.
200 OK

PAYMENT-REQUIRED Header Schema V2

JSON / Base64-encoded in header 
// Decoded from PAYMENT-REQUIRED header (base64)
{
  "scheme":    "exact",
  "network":   "eip155:8453",          // CAIP-2 — Base mainnet
  "maxAmount": "10000",               // In token base units (6-decimal USDC)
  "asset":     "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  "payTo":     "0xServerWalletAddress",
  "resource":  "https://api.example.com/data",
  "description": "Real-time market snapshot"
}
Note on V2 Header Rename

V1 used non-standard X-PAYMENT and X-PAYMENT-RESPONSE headers. V2 drops the X- prefix (RFC convention for experimental headers was deprecated in RFC 6648). All new implementations should use PAYMENT-SIGNATURE and PAYMENT-RESPONSE. V2 SDKs remain backward-compatible with V1 servers.

Supported Networks CAIP-2

Base and Solana are most active. Free public Coinbase facilitators available for both.

03

Encryption Standard

EIP-3009, EIP-712 typed-data, and the cross-layer trust model.

Core Insight

x402 does not invent a new cryptographic primitive. It combines two Ethereum standards — EIP-712 (structured data hashing + signing) and EIP-3009 (gasless token transfer authorization) — to produce a payment payload that is verifiable both off-chain (by the facilitator) and on-chain (by the USDC contract).

EIP-712 — Typed Data Signing

Structures arbitrary data into a canonical hash that wallets can display to users in a human-readable format. The signature covers: domain separator (contract address + chain ID), type hash (the exact function signature), and the message fields. Prevents cross-contract replay by binding each signature to a specific domain.

EIP-3009 — TransferWithAuthorization

An ERC-20 extension that lets a token holder sign an off-chain authorization allowing a third party to move tokens on their behalf. The core function takes seven fields: from, to, value, validAfter, validBefore, nonce, and an EIP-712 signature. Enables gasless transfers — the facilitator sponsors gas, the payer only needs USDC.

PAYMENT-SIGNATURE Payload Structure

JSON — PAYMENT-SIGNATURE header value (base64) 
{
  "scheme":      "exact",
  "network":     "eip155:8453",
  "payload": {
    "signature":  "0xabc123...eip712sig",     // EIP-712 over the message below
    "authorization": {
      "from":        "0xAgentWallet",
      "to":          "0xServerWallet",
      "value":       "10000",              // USDC base units ($0.01)
      "validAfter":  0,
      "validBefore": 1748991600,           // Unix timestamp expiry
      "nonce":       "0x7f3a...random32bytes"  // Replay protection
    }
  }
}

Signature Field Reference

Field Type Description
from address Payer wallet. The agent's Ethereum address whose USDC balance will be debited.
to address Payee wallet. The server's payTo address from the 402 challenge.
value uint256 Amount in token base units. USDC has 6 decimals — $0.01 = 10000.
validAfter uint256 Unix timestamp. Signature not valid before this time. Usually 0.
validBefore uint256 Expiry timestamp. Signature invalid after this point — primary replay mitigation.
nonce bytes32 Random nonce. Consumed on-chain after first use. Prevents replay of the same auth.
signature bytes EIP-712 sig (r, s, v). Signs the EIP-712 typed hash of the authorization struct above.
Permit2 Path (Alternative)

For tokens without native EIP-3009 support, x402 V2 also supports Uniswap's Permit2 contract — a universal approval mechanism deployed on all major EVM chains. Permit2 brings the same gasless signed-transfer pattern to any ERC-20. The facilitator resolves which signing path to use based on the token contract queried at runtime.

Implementation Guide

Server-side protection, Python client agent, and Circle MPC wallet integration.

A — Protecting an Endpoint (Node/Express)

TypeScript / Express — x402 V2 
import express from 'express'
import { paymentMiddleware } from '@coinbase/x402-express'

const app = express()

// Wrap protected routes with payment middleware
app.use(
  paymentMiddleware('0xYourServerWalletAddress', {
    '/api/data': {
      amount:  '0.01',                           // USD value string
      asset:   '0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913',  // USDC Base
      network: 'eip155:8453'                     // CAIP-2
    },
    '/api/inference': { amount: '0.001', asset: 'USDC-BASE', network: 'eip155:8453' }
  })
)

app.get('/api/data', (req, res) => {
  res.json({ result: 'paid content' })
})

app.listen(3000)

B — Python Agent Client

Python 3.10+ — pip install x402-python 
import os
from x402 import create_client

# Wallet private key — load from env, never hardcode
PRIVATE_KEY = os.environ["AGENT_PRIVATE_KEY"]

# Build an x402-aware httpx client
client = create_client(
    private_key=PRIVATE_KEY,
    network="eip155:8453",       # Base mainnet
    max_amount="0.05",           # Spending cap per request (USD)
)

# First request returns 402; client auto-signs and retries
response = client.get("https://api.example.com/data")
print(response.json())

# Payment receipt is available in the response header
receipt = response.headers.get("payment-response")
print("tx:", receipt)

D — Circle MPC Wallet (Keyless Agent)

Recommended Pattern for AGI Agents

Circle's reference architecture provisions an MPC-backed developer wallet — the agent never holds raw private keys. When an x402 paywall is hit, the agent calls the Circle Signing API to produce the EIP-712 signature, then posts the result via PAYMENT-SIGNATURE. This is the canonical pattern for agent payment infrastructure with auditability.

Python — Circle SDK + x402 manual flow 
from cdp import CdpClient
import httpx, json, base64, time, os

cdp = CdpClient(api_key=os.environ["CDP_API_KEY"])
wallet = cdp.wallets.create(network_id="base-mainnet")

# Step 1: Probe the endpoint — expect 402
r = httpx.get("https://api.example.com/data")
assert r.status_code == 402

# Step 2: Decode payment requirements
req = json.loads(base64.b64decode(r.headers["payment-required"]))

# Step 3: Build EIP-3009 authorization struct
auth = {
    "from":        wallet.default_address,
    "to":          req["payTo"],
    "value":       req["maxAmount"],
    "validAfter":  0,
    "validBefore": int(time.time()) + 300,  # 5-min window
    "nonce":       os.urandom(32).hex(),
}

# Step 4: Sign via CDP (no raw key exposure)
sig = wallet.sign_typed_data(domain=build_domain(req), message=auth)

# Step 5: Encode and retry
payload = base64.b64encode(json.dumps({
    "scheme": "exact", "network": req["network"],
    "payload": { "signature": sig, "authorization": auth }
}).encode()).decode()

result = httpx.get("https://api.example.com/data",
    headers={ "payment-signature": payload })
print(result.json())

Security Considerations

Five known attack vectors from formal analysis (arXiv:2605.11781) and mitigations.

Formal Analysis — May 2026

A peer-reviewed paper formally analysed x402 and identified five concrete attack classes across the authorization, binding, replay, and web-layer handling stages. The core structural risk: x402 bridges a synchronous HTTP layer with an asynchronous blockchain settlement layer via an off-chain facilitator whose correctness is neither enforced by the protocol nor verifiable by the client at request time.

I
Authorization Stripping
A malicious or compromised server accepts payment but returns a stale or incorrect resource. The client has no in-band proof that the resource served corresponds to the payment authorization signed.
HIGH
II
Signature Replay
If validBefore is set far in the future and the nonce is reused (e.g., server logs it but doesn't enforce uniqueness on-chain), an attacker who captures a signed payload can resubmit it for additional payments.
HIGH
III
Web-Layer Binding Attack
A rogue x402 endpoint presents a legitimate-looking 402 challenge but substitutes its own payTo address or a high-value EIP-2612 Permit payload. Because wallets don't natively render EIP-712 structs, users/agents may sign without verifying the destination.
HIGH
IV
Facilitator Trust Gap
The facilitator's POST /verify response is trusted by the server with no on-chain proof at request time. A compromised facilitator can confirm payments that never settled, causing the server to serve resources for free.
MED
V
Cross-Chain Confusion
V1 used informal network strings ("base-sepolia"); V2 mandates CAIP-2 format. Mixed-version deployments may mis-route payments to the wrong chain or accept testnet authorizations on mainnet if chain ID validation is not enforced.
MED

Mitigation Checklist

AreaRecommendation
Replay Always set validBefore to ≤ 5 minutes from now. Use random 32-byte nonces. Maintain a nonce registry off-chain; cross-check with on-chain USDC nonce map.
Binding Agents must validate payTo against a trusted allowlist before signing. Never auto-sign 402 challenges from unknown servers beyond your maxAmount cap.
Facilitator For high-value flows, run your own facilitator or use a decentralised one (ChaosChain x402). Always verify the on-chain transaction hash before serving premium resources.
Chain Confusion Strictly enforce CAIP-2 identifiers. Reject any payment requirement whose network field doesn't match your configured chain. Never accept testnet IDs on production.
Spending Caps Implement per-tx, per-day, and per-domain spending caps at the agent wallet layer (ERC-4337 smart wallets support this natively with CardZero / AgentCore patterns).

AGI Framework Note — ENTITY / AiM

For multi-agent orchestration frameworks with Ollama-backed nodes, x402 enables per-inference monetisation of student-model outputs and autonomous resource procurement (vector DB queries, external data APIs) without human-in-the-loop billing cycles. The recommended pattern: provision each agent node with a CDP-managed wallet and enforce spending caps at the middleware layer. The LAP identity document can carry the agent's payTo address and per-session spending policy as a memory pointer, making payment intent an intrinsic part of agent identity.
